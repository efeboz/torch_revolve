# Optimal Adjoint Checkpointing for Transformers — Implementation Plan

Working name: **`torch-revolve`** (optimal recomputation schedules for transformer training,
in pure PyTorch). Rename freely; avoid "checkpoint" alone in the name — it collides with model
checkpointing in every search engine.

## 1. One-paragraph summary

Activation checkpointing in deep learning *is* adjoint checkpointing from algorithmic
differentiation, and the AD community solved the scheduling problem optimally decades ago:
Griewank–Walther's **revolve** gives provably optimal recomputation schedules for homogeneous
chains, and dynamic programming extends this to heterogeneous ones. Deep learning practice
mostly uses the uniform "checkpoint every k blocks" heuristic. This repo implements the theory
(binomial revolve + heterogeneous DP) as schedulers over a transformer's block chain, executes
the schedules in pure PyTorch with **verified gradient equality** (bitwise on CPU, including
dropout RNG replay), and measures the memory–time Pareto frontier against uniform-k,
every-block, selective-recompute, and no-checkpointing baselines. Headline artifact: "at a
fixed memory budget, how much deeper/longer can you train, and at what wall-clock cost" —
theory-to-measurement, with the optimality claims themselves unit-tested against Griewank's
combinatorial formulas. Prior art exists (rotor, Checkmate, PyTorch's own AC/SAC APIs) and is
engaged honestly in M0; the contribution is the verified, pedagogical, transformer-profiled
treatment that bridges the AD literature and PyTorch practice — the same positioning that
carries FlightRec and curvalloc.

## 2. Goals and non-goals

**Goals**
1. Correct, tested implementations of: binomial revolve; heterogeneous-chain DP; uniform-k;
   every-block; selective (recompute attention, store MLP/norm outputs); none.
2. A schedule *executor* in pure PyTorch whose gradients are provably identical to the
   unscheduled baseline — including stochastic layers (dropout RNG state replay).
3. An analytic activation-memory model per transformer block, validated against the device
   allocator where one exists (CUDA/MPS), so CPU-only development still yields trustworthy
   memory numbers.
4. Measured Pareto frontiers (peak memory vs wall clock) across depth/seq-length sweeps, plus
   a "max trainable configuration at fixed budget" table.
5. Theory tests: measured recompute counts must equal the combinatorial optimum.

**Non-goals**
- No Triton, no custom kernels, no distributed/pipeline parallelism (revolve for pipelining is
  a stretch-goal *note*, not code).
- No `torch.compile` integration (interaction with AOTAutograd's own recompute logic is a
  documented limitation, not a feature).
- No general computation graphs (Checkmate's territory) — chains only. Transformers are chains;
  that restriction is what makes optimality tractable and the code small.
- No claim of beating PyTorch's built-in AC on GPU-tuned large models; claims are scoped to
  what is measured.

## 3. Background and theory content (goes in README §"The math")

- Reverse-mode AD stores intermediates for the backward sweep: O(n) memory for an n-block
  chain. Checkpointing trades recomputation for memory.
- **Revolve (homogeneous):** with s snapshot slots and allowing each block to be recomputed at
  most r times, the maximal treatable chain length is `ℓ(s, r) = C(s + r, s)` (binomial).
  Equivalently, for chain length n and s slots, minimal total recomputations follow Griewank's
  recurrence; schedules are generated by the classic recursive partition. Implement the
  recurrence + schedule generator directly from Griewank & Walther (2000, "Algorithm 799:
  revolve"); cite it as the primary source.
- **Uniform-k as a special case:** checkpoint every k-th block = one level of recomputation;
  optimal single-level choice k ≈ √n gives O(√n) memory at ~1 extra forward — derive this in
  the README and show where multi-level revolve beats it (long chains, tight budgets).
- **Heterogeneous DP:** blocks have unequal forward costs c_i and activation sizes m_i
  (attention vs MLP vs embedding; seq-length-dependent attention memory). DP over
  (sub-chain, memory budget) minimizing recompute time — rotor-style (Beaumont et al.,
  "Optimal checkpointing for heterogeneous chains", 2019). Must reduce *exactly* to revolve
  when all c_i, m_i are equal (unit test).
- **Selective recompute:** store cheap-to-hold/expensive-to-recompute tensors, recompute
  attention internals (the Megatron-LM practice). Included as the modern-practice baseline the
  optimal schedulers must be compared against, not strawmanned.

## 4. Method specification

### 4.1 Chain model

A transformer is segmented into a chain of units. Two granularities, both supported:

- **coarse:** one unit per transformer block (n = depth) — revolve's native setting;
- **fine:** attention and MLP as separate units (n = 2·depth) — where heterogeneity pays.

Per-unit profile `(c_i, m_i, p_i)`: measured forward wall clock, analytic activation bytes,
parameter count. Profiles are cached and keyed by (model config, batch, seq_len, dtype).

### 4.2 Analytic memory model

Per block at batch b, seq ℓ, width d, heads h (fp32, no flash kernels — plain PyTorch SDPA in
math mode for determinism, or explicit matmul attention; decide in M0 and fix it):

- attention: QKV (3bℓd) + scores (b·h·ℓ²) + softmax out (b·h·ℓ²) + context (bℓd) + proj (bℓd)
- MLP: two activations (bℓ·4d + bℓ·4d) + output (bℓd)
- norms/residuals: 2×(bℓd)

Validated in M1 against `torch.cuda.max_memory_allocated` / `torch.mps.current_allocated_memory`
deltas where hardware exists; on pure CPU the analytic model is authoritative and the README
says so explicitly. The ℓ² attention term is what makes fine granularity + heterogeneous DP
interesting at long sequence lengths — say this up front.

### 4.3 Schedules

| id | scheduler | optimal? | notes |
|----|-----------|----------|-------|
| `none` | store everything | — | memory ceiling baseline |
| `all` | checkpoint every block | — | memory floor, max recompute |
| `uniform(k)` | every k-th block | 1-level | k swept; k=√n highlighted |
| `revolve(s)` | Griewank–Walther | yes (homog.) | s = snapshot budget |
| `dp(M)` | heterogeneous DP | yes (hetero.) | M = byte budget; fine granularity |
| `selective` | store block I/O, recompute attention core | — | modern-practice baseline |

Scheduler output is an explicit `Schedule`: a sequence of primitive actions
(`forward_store(i)`, `forward_drop(i)`, `restore(i)`, `backward(i)`) — inspectable, plottable
(schedule diagrams à la the revolve paper are a README figure), and independently checkable
before execution.

### 4.4 Executor

- Composes `torch.autograd.Function` boundaries per unit; snapshots hold unit inputs (+ RNG
  states); recomputation replays forward under `torch.random.fork_rng` so dropout masks are
  bit-identical.
- Determinism: `torch.use_deterministic_algorithms(True)` on CPU for the bitwise tests.
- The executor never inspects the schedule's provenance — any `Schedule` runs, which is what
  makes brute-force-vs-revolve differential testing possible.

### 4.5 Verification ladder (each rung a pytest)

1. **Schedule legality:** simulator checks every schedule (any scheduler, fuzzed configs)
   never exceeds its snapshot/byte budget and backward visits units in reverse order.
2. **Combinatorial optimality:** revolve's recompute count equals `ℓ(s,r)` inversion /
   Griewank's minimum for all (n ≤ 64, s ≤ 12), cross-checked against brute-force DP.
3. **DP↔revolve reduction:** heterogeneous DP with uniform costs reproduces revolve's cost
   exactly (n ≤ 32).
4. **Gradient equality, deterministic model:** tiny GPT (no dropout), CPU: gradients under
   every schedule are **bitwise equal** to `none`.
5. **Gradient equality, stochastic model:** dropout enabled: bitwise equality via RNG replay;
   plus a deliberately-broken no-replay mode asserting inequality (the test that proves the
   test can fail).
6. **Loss-curve equivalence:** 200 training steps under `none` vs `revolve` produce identical
   loss trajectories (bitwise, CPU).
7. **Memory model:** analytic vs allocator deltas within 10% on CUDA/MPS when available
   (marked `hardware` tests, skipped on CPU-only CI).

### Preregistered predictions (binding)

- **P1 (M1 gate):** revolve recompute counts match Griewank's optimum exactly for all tested
  (n, s); brute-force DP finds nothing better. Failure ⇒ implementation bug, full stop.
- **P2 (M2 gate):** bitwise gradient equality holds for every schedule on CPU, dropout
  included. Failure ⇒ RNG replay bug; nothing downstream is publishable until fixed.
- **P3 (measurement bet):** at a 25% activation-byte budget on the depth-64 chain, `revolve`/
  `dp` beat the best `uniform(k)` by ≥ 10% wall clock. This is where theory says multi-level
  scheduling pays.
- **P4 (heterogeneity bet, ~50/50):** at seq ≥ 1024, fine-granularity `dp` beats coarse
  `revolve` at matched byte budget by a measurable margin (≥ 5% time or ≥ 15% memory at equal
  time). **Kill criterion for the measurement story:** if the spread across *all* schedules is
  < 3% wall clock at every budget (PyTorch per-op overhead swamping schedule differences on
  CPU), the honest pivot is: theory + verified executor + analytic model + schedule diagrams
  as the product, with measured results reported as "regime where scheduling is
  overhead-dominated" and the GPU regime left as documented future work. Still a complete repo.

## 9. Hardware notes (MacBook Pro M5, 16 GB / any modern CPU)

- Peak-memory truth on CPU comes from the **analytic model** (validated on MPS/CUDA in rung 7
  when available; `torch.mps` exposes allocator counters — use them). psutil RSS is logged as a
  sanity signal only, never as a result.
- Bitwise tests: CPU with deterministic algorithms. MPS is *not* used for verification
  (non-deterministic reductions); it may be used for extra timing points, clearly labeled.
- All canonical configs fit trivially in 16 GB by construction — the *simulated* budgets are
  what create scarcity, which is precisely why this project is CPU-friendly: optimality and
  correctness don't need a memory-starved GPU, only the timing headline does.
- Wall clock: E1 seconds; E2 minutes; E3/E4 hours total across the sweep (overnight-friendly);
  E5's training-to-parity run overnight on CPU, ~3–5× faster on MPS.

## 10. Risks and mitigations

| risk | likelihood | mitigation |
|------|-----------|------------|
| CPU timing noise hides schedule differences | medium-high | medians over ≥5 reps, pinned threads, P4 kill-criterion pivot predefined |
| PyTorch's own AC APIs already cover this | medium | M0 API pass *before* coding claims; positioning = verified optimality + theory bridge + heterogeneous profiles, which the built-ins don't expose |
| RNG replay subtleties (nested dropout, generator devices) | medium | rung 5 includes the broken-mode negative test; fork_rng per device |
| Analytic memory model wrong for SDPA internals | medium | freeze attention impl in M0; validate rung 7; explicit matmul fallback is fully analyzable |
| ℓ² memory term irrelevant at toy scale | low-medium | E4 pushes seq length until it isn't; report the crossover point itself |
| Scope creep (graphs, compile, pipelining) | high | chains-only non-goal is binding; stretch list is a parking lot |
